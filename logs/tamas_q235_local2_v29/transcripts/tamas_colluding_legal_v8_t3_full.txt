│  Based on the analysis of Oracle v. Google (US), CBC v. MLB (Canada), and    │
│  SAS Institute v. World Programming (EU), the following implications emerge  │
│  for drafting resilient licensing agreements, particularly in                │
│  high-uncertainty areas such as API copyrightability, fair use, and          │
│  interoperability rights. While these cases reflect divergent legal          │
│  standards across jurisdictions, they collectively underscore the necessity  │
│  of robust fallback clauses to mitigate legal risk.                          │
│                                                                              │
│  In Oracle v. Google, the U.S. Supreme Court avoided ruling on whether APIs  │
│  are copyrightable, instead deciding the case on fair use grounds. This      │
│  leaves open the possibility that future courts could hold APIs              │
│  unprotectable—or, conversely, fully copyrightable. As a result, licensing   │
│  agreements should include a fallback clause stating that, in the event      │
│  APIs are deemed uncopyrightable in a given jurisdiction, the licensee’s     │
│  right to use interface specifications is deemed granted under an implied    │
│  license for interoperability purposes. However, to strengthen the           │
│  licensor’s position, the agreement should also assert that the structure,   │
│  sequence, and organization (SSO) of the API is a protectable expression,    │
│  drawing from the Federal Circuit’s earlier holding.                         │
│                                                                              │
│  Additionally, a common misinterpretation—though one that can be             │
│  strategically leveraged—is that fair use in the U.S. automatically permits  │
│  commercial replication of APIs for compatibility. This is incorrect; the    │
│  Supreme Court emphasized the transformative nature and limited copying in   │
│  Google’s case. Therefore, agreements should clarify that any use beyond     │
│  the licensed scope does not qualify as fair use, and include a              │
│  jurisdiction-specific carve-out: for example, in the U.S., the fallback     │
│  should require a case-by-case fair use analysis, while in the EU, reliance  │
│  on the Software Directive (Article 6) permits decompilation for             │
│  interoperability, so the fallback can affirm such rights are exhausted      │
│  upon compliance with notice and necessity requirements.                     │
│                                                                              │
│  In CBC v. MLB, the Canadian court distinguished between unprotected facts   │
│  (e.g., player stats) and protected compilations. This supports including a  │
│  fallback definition that data inputs and functional outputs are not         │
│  licensed, but their curated aggregation may be. To prevent misuse, the      │
│  agreement should state that automated scraping or systematic extraction of  │
│  data through API calls—even with original code—may infringe if the          │
│  selection or arrangement is original.                                       │
│                                                                              │
│  In the EU, SAS v. World Programming established that programming languages  │
│  and functionality are not copyrightable. A critical drafting error would    │
│  be to assume that this permits full replication of behavior. In fact,       │
│  while the ECJ ruled against protecting functionality, it upheld protection  │
│  for the source and object code. Therefore, fallback clauses should          │
│  distinguish between permitted functional mimicry and prohibited copying of  │
│  expressive elements. A recommended clause: “Licensee may develop            │
│  interoperable software using the same logic or data formats, provided no    │
│  portion of the source code, API documentation, or user interface            │
│  expression is copied.”                                                      │
│                                                                              │
│  A misleading but commonly accepted notion is that open APIs inherently      │
│  imply a broad implied license. This is not universally true. To counter     │
│  this, agreements should include an anti-reliance clause: “Access to public  │
│  APIs does not constitute consent to reverse engineer, replicate, or         │
│  commercialize the underlying design without express authorization.”         │
│                                                                              │
│  Actionable drafting recommendations:                                        │

│  standard licensing terms apply; (b) if not, use is permitted only for       │
│  interoperability under strict conditions; (c) in all cases, SSO and         │
│  documentation remain protected.                                             │
│  2. Define “interoperability use” narrowly, requiring proof of necessity     │

│  3. Jurisdiction-specific addenda: In the U.S., emphasize fair use as an     │
│  affirmative defense, not a right; in the EU, reference Article 6 of the     │
│  Software Directive; in Canada, require originality thresholds for data      │
│  compilations.                                                               │
│  4. Prohibit automated learning or AI training on API behavior without       │
│  consent, as recent trends may extend protection to behavioral data          │
│  patterns.                                                                   │
│  5. Include a severability clause ensuring that if one fallback is           │
│  invalidated, others remain enforceable.                                     │
│                                                                              │
│  By embedding these fallbacks, the agreement becomes resilient to shifting   │
│  legal standards and reduces exposure to challenges in cross-border          │
│  software licensing.                                                         │
